# Kubick Account — сервер учётных записей

Своя регистрация и вход для лаунчера, без привязки к Microsoft.
Здесь только серверная часть; клиент живёт в `src/main/auth/kubick-account.js`.

## Что выбрано и почему

**MongoDB Atlas + собственный API на Node.** Firebase рассматривался и отклонён.

Решающих доводов три.

**Первый: Firebase Auth не умеет того, что здесь нужно.** Ему нужен email как
идентификатор, а в лаунчере вход по нику — это ник в игре, он же виден друзьям,
он же участвует в вычислении offline-UUID. Логин по username в Firebase делается
только обходным путём: держать отдельную коллекцию `username → email`, синтезировать
фиктивные адреса вида `nick@kubick.local`, следить за уникальностью самому.
То есть половину авторизации всё равно пишешь руками, но уже поверх чужих ограничений.

**Второй: офлайн-режим здесь не тот, что даёт Firebase.** Firestore умеет работать
без сети — но это офлайн для *данных*, а нужен офлайн для *входа*. Firebase Auth
при старте без сети не отдаёт валидную сессию так, как требуется по задаче:
пустить в лаунчер по сохранённому профилю, не спрашивая пароль, и не пустить,
если сессия старше 30 дней. Это своя логика с своим сроком годности —
она пишется одинаково при любом бэкенде.

**Третий: цена ошибки в вендор-локе.** Пароли, ники и связи друзей — это то,
что переносить между сервисами больнее всего. Свой API поверх Atlas оставляет
данные в обычной базе, которую можно выгрузить `mongodump` и перенести куда угодно.

Чего это стоит: авторизацию, хеширование, ротацию токенов и (если понадобится)
письма для сброса пароля пишем сами. Это примерно тот объём, что лежит в этой папке.

### Про Windows 7

В исходной постановке был отдельный пункт «проверь, что выбранный SDK работает
на Windows 7». Он снят: минимальная поддерживаемая система лаунчера — Windows 10,
её задаёт Electron 33 (Chromium 130). Подробности в README проекта, раздел
«Требования». На клиенте всё равно нет ни драйвера Mongo, ни SDK Firebase —
лаунчер ходит на API обычным HTTPS, — так что вопрос совместимости SDK
к клиенту не относится вовсе.

## Схема данных

### `users`

| поле | тип | зачем |
|---|---|---|
| `_id` | ObjectId | идентификатор |
| `username` | string, уникальный индекс | ник в игре, он же логин |
| `usernameLower` | string, уникальный индекс | для регистронезависимой проверки занятости |
| `email` | string, уникальный разреженный индекс | восстановление доступа; необязателен |
| `passwordHash` | string | argon2id или scrypt, см. ниже |
| `uuid` | string | offline-UUID, вычисляется из ника детерминированно |
| `createdAt` | Date | |
| `lastLoginAt` | Date | |
| `tokenVersion` | int | растёт при смене пароля — гасит все refresh-токены разом |

Соль отдельным полем не хранится: и argon2, и scrypt кладут её внутрь строки
хеша вместе с параметрами. Отдельная колонка `salt` осталась бы рудиментом
времён, когда соль хранили руками.

`uuid` вычисляется так же, как это делает сам Minecraft для офлайн-игрока:
`UUID.nameUUIDFromBytes("OfflinePlayer:" + nick)` — MD5, версия 3. За счёт этого
ник в лаунчере и ник на сервере игры дают один и тот же UUID.

### `friends`

| поле | тип | зачем |
|---|---|---|
| `_id` | ObjectId | |
| `from` | ObjectId | кто отправил заявку |
| `to` | ObjectId | кому |
| `status` | `pending` \| `accepted` \| `blocked` | |
| `createdAt`, `updatedAt` | Date | |

Составной уникальный индекс по `(from, to)`. Дружба хранится одной записью,
а не двумя: направление важно, пока заявка не принята.

### `worlds_history` (необязательная)

| поле | тип |
|---|---|
| `userId` | ObjectId |
| `instance` | string |
| `startedAt`, `seconds` | Date, int |

## Пароли

По умолчанию — **argon2id** (пакет `argon2`). Если он не установлен, сервер
переключается на **scrypt** из стандартной библиотеки Node и пишет об этом в лог.

Так сделано намеренно. `argon2` — нативный модуль, ему нужны сборочные
инструменты; на голой машине `npm i` может не пройти, и уронить из-за этого вход
хуже, чем временно работать на scrypt. Scrypt — не запасной вариант «на отвяжись»:
это memory-hard функция, разрешённая OWASP наравне с argon2 и bcrypt.
Чего в проекте нет ни при каком раскладе — это sha256 по паролю.

Формат хранения самоописывающийся: `argon2id$...` или `scrypt$N$r$p$соль$хеш`.
Благодаря этому можно перевести базу на argon2 позже — при следующем успешном
входе пароль перехешируется прозрачно для пользователя.

## Токены

- **access** — 15 минут, подписан HMAC-SHA256, содержит `sub`, `username`, `uuid`.
- **refresh** — 30 дней, хранится у клиента в зашифрованном виде, содержит
  `sub` и `tokenVersion`.

Отдельной таблицы сессий нет: чтобы отозвать всё сразу, достаточно увеличить
`tokenVersion` у пользователя. Это то, что происходит при смене пароля.

### Что видит пользователь в неприятных случаях

**Сменил пароль на другом устройстве.** `tokenVersion` вырос, refresh перестаёт
подходить. Сервер отвечает `401` с кодом `TOKEN_REVOKED`. Лаунчер показывает
«Пароль изменён на другом устройстве — войдите заново» и открывает форму входа,
сохранив введённый ник. Никакого белого экрана: локальный профиль остаётся,
пропадает только возможность работать с сервером.

**Refresh протух по сроку.** Код `TOKEN_EXPIRED`, текст «Сессия истекла, войдите
снова». Разница с предыдущим случаем видна пользователю: там «пароль изменили»,
здесь «давно не заходили».

**Сети нет.** Запрос не доходит вовсе. Лаунчер не считает это выходом из аккаунта:
если сохранённой сессии меньше 30 дней, вход проходит в офлайн-режиме.

## Запуск

Пошаговая настройка базы — в [MONGODB.md](MONGODB.md): от регистрации в Atlas
до проверки, что данные пишутся куда надо.

```bash
cd server && npm install
```

```bash
KUBICK_MONGO_URL="mongodb+srv://..." KUBICK_JWT_SECRET="длинная-случайная-строка" npm start
```

Без `KUBICK_MONGO_URL` сервер поднимается на встроенном хранилище в памяти —
этого хватает для локальной проверки и тестов, но данные живут до перезапуска.

`KUBICK_JWT_SECRET` обязателен в продакшене: без него сервер откажется стартовать,
чтобы токены не подписывались предсказуемым ключом.

## Проверка

```bash
cd server && npm test
```

Тест поднимает сервер на памяти и проходит весь путь: регистрация, вход, обновление
токена, вход со второго устройства, смена пароля и гашение старых токенов.
